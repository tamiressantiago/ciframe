# Introduce SQLite persistence in a volume for the custom sequences catalog

The project kept the sequence catalog only in code (`main.py` with 6 hardcoded sequences) and searches used precomputed tags in the CSV. With the need to let any visitor register a new famous chord sequence (without login) and use it to search, that catalog is no longer static: registered sequences must exist across runs of the local-only Docker container.

We decided to use the Python standard library `sqlite3` to store only the sequence catalog. Songs and genres still come from the CSV, loaded in memory as today. The database will have a `sequencias` table with an integer `id` and the `acordes` stored as text with chords separated by spaces (e.g., `Bm G D A`), seeded on first run with the 6 original sequences. The file will live in a volume, since the `Dockerfile` currently declares no volume and a file written inside the container is lost when the container is recreated; to keep the sequences, a volume must be mounted by changing the run command to something like `docker run -p 8080:8080 -v ciframe-db:/app/data/db ciframe`.

This choice was made because SQLite already ships with the image, requires no new dependency in `requirements.txt`, writes to a local file, and is viable in the single local-only container documented in `docs/adr/0001-local-only-docker-deploy.md`. The trade-off is precisely the need for persistence via a volume: without it, the sequences are lost when the container is recreated. In addition, sequence search will now be computed in real time from each song's cifra, using the criterion that reproduces the current tags: the song cannot have chords outside the sequence, and the sequence must appear in exact order and sequentially at least once (checked in that order).
